# ADR-016: EC-02's Enforcement Boundary Is Create/Destroy/Build Only — Supervision, Discovery, and Exec Stay TypeScript-Native

Status: accepted, 2026-09-02 (Phase 9, EC-02). Scopes the "rewire container-runner.ts's three privileged functions to call internal/kernel exclusively" task named in `docs/roadmap-to-v1.md` and closes the design gap this ADR's own investigation found.

## Context

Reading the real `src/drivers/docker-driver.ts` and `src/drivers/types.ts` in full (not assumed from `container-runner.ts`'s call sites alone) surfaced a materially larger `SessionDriver` contract than `internal/kernel`'s current `Executor` interface models:

- `prepare(spec)` does `docker create` with a full hardening posture, `--rm`, entrypoint/command splitting, per-container labels, contributed-env override ordering, and a driver-private network flag — then a **separate, long-lived** `docker start --attach` process whose stdout/stderr and exit code drive session supervision (`onTerminal`/`afterStart`).
- `stop()` does `docker stop -t <grace>` (graceful, with a kill-the-attach-process fallback) then `docker rm --force` — not the single unconditional `docker kill` the kernel's `handleKill` currently issues.
- `listSessions`/`watchSessions`/`reapResidue` do `ps -a`/`docker events`/`network ls`+`rm` for adoption, discovery, and orphan cleanup — read/observational operations, not mutations of a spec's admission.
- `execSpec()` is pure description ("the driver never performs it") — the actual `docker exec` invocation happens wherever the caller (CLI dispatch, an operator shell) runs the returned argv, not inside the driver at all.
- The network flag (`networkArgsFor`) is injected once at driver **construction** (`src/drivers/index.ts`: `dockerNetworkArgs`, a fixed function of the install's `EGRESS_NETWORK` constant) — never per-request, never attacker-influenced.

`internal/kernel`'s `Executor` (`Wake`/`BuildImage`/`Kill`) and `mount.Session` (explicitly documented as "the subset of SessionSpec this package's rules read") do not carry the fields a real `docker create` needs (image, command, entrypoint args, per-container labels, stop-grace) and model `Kill` as an unconditional `docker kill` rather than the graceful stop-then-rm the real driver performs. Separately, `exec.go`'s `BuildImage` was found to silently discard the `dockerfile` parameter (`_ = dockerfile`) rather than piping it to `docker build -f -` — harmless only because nothing calls it in production today.

A literal "the kernel becomes the sole path for everything `DockerSessionDriver` does" would require: extending the wake payload to a near-complete `SessionSpec`, a new streaming sub-protocol for attach-based supervision (the socket is currently strict request/response), and moving discovery/adoption/orphan-reaping behind the kernel too. That is a multi-day redesign touching the live container runtime's adoption and crash-recovery behavior — exactly the kind of change that should not proceed without the user's explicit sign-off, given this session cannot run the TypeScript test suite itself and depends on the user pasting back results from their own Mac.

## Decision

**EC-02's enforcement boundary is the three operations that actually commit a privileged, admission-relevant effect: container creation (the full validated spec), teardown, and image build.** The kernel becomes the sole path for these. Supervision (the attach process and its exit-code/stderr stream), discovery (`listSessions`, `watchSessions`, `reapResidue`), and exec-argv description stay TypeScript-native, operating against containers the kernel itself created and named — never choosing what gets created or destroyed, only observing and attaching to it.

This is a deliberate, narrower reading of "exclusive enforcement" than a full driver replacement, chosen because:

1. **It closes the actual gap.** The security-relevant question LAW-07 asks is "can an admission decision (the mount spec, the run-as identity, the resource caps, the image tag and Dockerfile, the CLI-restart guard's cli_scope/approval check) be bypassed by a compromised TypeScript host process constructing its own `docker` invocation instead of going through the kernel." Supervision and discovery never make an admission decision — they observe or attach to a container the kernel already validated and created. Moving them behind the kernel too would not close any additional bypass; it would only add engineering surface.
2. **Attach supervision after kernel-side start is safe as designed.** The kernel performs `docker create` (full validated argv) then a plain, non-attached `docker start`. TypeScript's existing supervision step then runs `docker attach --no-stdin <name>` against the already-running container the kernel named and returned — `attach`, not `start --attach`, because the container is already running; this needs no new protocol, since `docker attach` is exactly Docker's designed mechanism for observing an already-running container's console from a separate process.
3. **The container name is kernel-derived, never caller-supplied**, extending the discipline `handleKill` already established for container-name resolution: `internal/kernel` ports `agentContainerName`'s hashing scheme itself and returns the name it used in `CapabilityResponsePayload`, so TypeScript's supervision/inspection steps use whatever the kernel actually created — never a name TypeScript computed and the kernel merely trusted.
4. **The network flag becomes kernel startup configuration**, not a per-request field — `nanogo serve` gains an optional `-docker-network` flag mirroring `dockerNetworkArgs`'s own fixed, install-level nature, keeping "no caller-supplied flags" intact rather than accepting an argv fragment from the request.
5. **Kill becomes a graceful stop-then-remove**, matching the real driver's `stop()` exactly (`docker stop -t <grace>` then best-effort `docker rm --force`) rather than the unconditional `docker kill` `handleKill` issues today — a real behavioral gap this ADR's investigation found, fixed as part of this change. Grace seconds are read from the kernel's own registry (recorded at wake time from the validated spec), never re-asserted by the caller at kill time.
6. **The guard-policy consult point (`internal/guardpolicy`, ADR-015) attaches to `container.wake`/`container.kill` (the CLI-restart path) and `container.build_image` (the self-mod install_packages path)** via an optional `GuardContext` on `CapabilityRequestPayload` — present only when TypeScript's guarded call sites (the `restart` CLI command's dispatch, and `self-mod/apply.ts`'s install flow) populate it; absent for every ordinary, ungated lifecycle wake/kill/build, which is not newly gated by this change (it was never gated in TypeScript either).

## What is deferred, named rather than silently dropped

Full driver replacement — `listSessions`/`watchSessions`/`reapResidue` behind the kernel, and the streaming sub-protocol attach-based supervision would need if it moved server-side — is out of scope for EC-02 and not assumed for a future phase by default; it would need its own scoping pass if ever undertaken, given the protocol redesign and adoption/crash-recovery risk involved.

## Implementation

Go-side, this ADR's accompanying change: `internal/kernel` gains `ContainerName`/`LabelsForKey` (ported from `agentContainerName`/`labelsForKey`), `mount.Container`/`Session` gain the realization-only fields `docker create` needs (image, command, args, per-container labels, stop-grace), `exec.go`'s `Wake` builds the complete real argv (fixing the missing `HardeningPosture`, `--rm`, and network-flag gaps) and returns the kernel-derived name, `Kill` performs graceful stop-then-remove using grace seconds recorded at wake time, and `BuildImage` actually pipes the Dockerfile to `docker build -f -` via stdin (fixing the silent-discard bug). `capability.go` gains the optional `GuardContext` consult point wired to `internal/guardpolicy`.

TypeScript-side — a new kernel client, `docker-driver.ts`'s `prepare`/`stop` rewired to call it, and the CLI-restart/self-mod call sites populating `GuardContext` — is tracked as the remaining, not-yet-started half of EC-02, to be built and verified against the user's real Mac test loop before being called complete.
