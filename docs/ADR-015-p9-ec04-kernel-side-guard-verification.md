# ADR-015: EC-04's Restart/Self-Mod Guard Slice Is Enforced By Independent Kernel-Side Verification, Not a Decision Mirror

Status: accepted, 2026-09-02 (Phase 9, EC-04, resolving the open question `EC-04-guard-scope-design-notes.md` raised and deliberately left open).

## Context

LAW-07 requires the privileged effect (here, `container.kill`/`container.wake`, reached via `ncl groups restart`) to be *physically impossible* to trigger except through the Go kernel. `EC-04-guard-scope-design-notes.md` established that the narrow slice of `guard.ts` in scope for Go parity — `src/cli/guard.ts`'s `commandDecide` as consulted for the `restart` command, plus the `install_packages`/`add_mcp_server` self-mod gate that precedes an image rebuild — is exactly the decision logic standing between an agent and the three Docker-facing kernel capabilities.

That document also identified the gap a naive port would leave open: `internal/kernel`'s `handleCapabilityRequest` has no caller-identity or authorization concept today. A Go package that mirrors `commandDecide`'s *decision* (tested against the 12 golden fixtures) but is consulted only by a TypeScript call site before it calls the kernel client delivers nothing LAW-07 asks for — any other TypeScript code path that calls the kernel client directly bypasses the mirror entirely, because the kernel itself never asks. This is the same class of gap the kernel already refuses to accept for container names: `TestCapabilityRequest_Kill_ResolvesNameFromOwnRegistry_NotFromCaller` exists precisely because a caller-supplied fact is not a fact the kernel can rely on for a security decision.

Two ways to close it were on the table:

1. **Kernel-side independent verification.** Extend the capability payload to carry the request's claimed identity (actor kind, agent group ID) and, when relevant, an approval-grant reference. Then have the kernel look up the two facts that actually decide the outcome (`cli_scope` from `container_configs`, and grant liveness/match from `pending_approvals`) itself, directly from the shared central SQLite DB it already opens via `WithSessionDB`. The kernel computes the decision; it does not trust a caller-computed one.
2. **Accept the limit and document it.** Treat a compromise inside the TypeScript host process as an irreducible single-process trust boundary no Go-side change can close, and say so plainly rather than claiming a security property that isn't real.

## Decision

**Both, deliberately combined, because they answer two different questions.**

The kernel will independently verify every fact that (1) is not identity itself and (2) already lives in shared, host-owned state the kernel can read on its own: `cli_scope` for the claimed agent group, and the liveness/action/payload match of a claimed approval grant. This is option 1, and it is not optional. It is what actually converts "TypeScript decided, Go trusted it" into "Go decided, from state it read itself," which is the entire point of EC-04 existing as a kernel-side task rather than a TypeScript-side one. Concretely, the new `internal/guardpolicy` package (this ADR's accompanying implementation) takes a `CLIScopeLookup`/`ApprovalLookup` pair backed by real SQL against `container_configs`/`pending_approvals`, never a caller-supplied `cli_scope` string or a caller-asserted "already approved" boolean. This mirrors the discipline `mount`'s symlink resolution and `capability.go`'s own-registry container-name resolution already established.

What the kernel does **not** independently verify, and cannot, in v1: **actor identity itself** — that a given request genuinely originates from agent group `X` and not some other caller impersonating it. In this architecture, the TypeScript host process is the sole terminus of every per-container connection (the socket/session plumbing that tells the host "this bytestream is agent group X's container" lives entirely in TypeScript; the Go kernel's only peer is the host process itself, communicating over one shared Unix socket). The kernel has no independent channel to that fact in v1 — it can demand the host assert it, but it cannot cross-check the assertion against anything the host doesn't also control. A compromised TypeScript host process could assert a false agent-group identity and the kernel would have no way to catch it.

This is option 2's honest half, recorded here: **closing the identity-assertion gap is out of scope for v1.** It would require either (a) per-container credentials issued and verified independently of the host process — architecturally close to what `internal/credentialbroker` was prototyping, and ADR-014 already declined to wire that into v1 for good reasons — or (b) the kernel terminating per-container connections itself, which is a materially larger redesign than "Enforcement Closure" as scoped. Neither is undertaken here.

## What this buys, precisely

Before this ADR, the entire restart/self-mod guard decision — cli_scope, cross-group checks, approval-hold satisfaction, everything — lived in a code path the kernel never saw, reachable exactly once from one call site with no structural guarantee that call site was the only path to the capability. After it: the kernel independently confirms cli_scope and grant validity from its own read of shared state on every `container.kill`/`container.wake` request tagged as CLI-restart-triggered, regardless of which TypeScript code path reached the kernel client — closing the specific bypass `EC-04-guard-scope-design-notes.md` named. What remains unclosed is narrower and named precisely: a compromised host process can still lie about *whose* request this is. That is a real, acknowledged limit, not an oversight. The compatibility/security report (P10-04) should state it in exactly these terms — "the kernel independently enforces scope and approval state; it trusts the host process's identity assertion" — rather than either overclaiming full LAW-07 coverage or dismissing the work as merely a decision mirror.

## What would change this decision

A future v1.1 that wires `internal/credentialbroker` (or an equivalent per-container credential mechanism) to let the kernel authenticate *which* container is asking, independent of the host process's say-so, would close the remaining gap and should revisit this ADR's "not independently verified" section. At that point, actor identity moves from the "trusted assertion" column to the "independently verified" column, alongside cli_scope and grant state today.

## Implementation

`internal/guardpolicy` (new package, this same change): a Go port of `commandDecide` (generic, parameterized by a `CommandSpec` exactly as `CommandDef` parameterizes the TypeScript original) plus the `install_packages`/`add_mcp_server` self-mod gate, wrapped with the same grant-satisfaction semantics `guard.ts`'s `guard()` applies on top of `decide()`. Tested against all 12 golden fixtures from `fixtures-guard-catalog.test.ts` (lines 632-747) reproduced verbatim as Go table tests, plus the self-mod gate's three fixtures. `CLIScope`/`PendingApproval` lookups run real SQL against `container_configs`/`pending_approvals` — the same tables TypeScript's migrations 014/015 and the `pending-approvals` migration already create in the production central DB. This package creates neither table itself outside its own tests, following `internal/session`'s established discipline of never asserting ownership of a table TypeScript owns.

Wiring this package into `internal/kernel/capability.go`'s `handleCapabilityRequest` — extending `CapabilityRequestPayload` with the actor/command/grant fields it needs, and gating `container.kill`/`container.wake` on its verdict when a request is tagged as CLI-restart-triggered — is EC-02's remaining work, tracked there rather than here, since it is inseparable from the TypeScript kernel-client design EC-02 is building.
