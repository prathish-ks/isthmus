# Message Flow Trace (P1-02)

A read-only trace of one real message end-to-end through NanoClaw's host + container, from the moment it arrives to the moment a reply reaches the user. No code was changed to produce this — annotations only, cross-referenced against source already read for P1-01 plus the additional files read for this task (`src/channels/cli.ts`, `src/channels/channel-registry.ts`, `src/command-gate.ts`, `src/delivery-guard.ts`, `container/agent-runner/src/index.ts`, `container/agent-runner/src/poll-loop.ts`, `container/agent-runner/src/mcp-tools/core.ts`, `container/agent-runner/src/mailbox/index.ts`, `container/agent-runner/src/db/messages-out.ts`).

**Message traced**: a plain chat message typed into a connected CLI terminal (`bash nanoclaw.sh`'s built-in chat client, or `scripts/chat.ts`), chosen because it needs no external platform credentials and exercises the exact same router/session/mailbox/container/delivery pipeline every channel adapter shares. Where a real platform (WhatsApp, Telegram, Discord…) differs, it differs only in the adapter at the two ends (inbound parsing, outbound `deliver()`) — everything in between is identical.

Per the second-opinion review folded into this task's scope, every step below is annotated with **which process currently holds the authority to cause the real-world effect**, not just which function decides it.

## The trace

**1. Terminal → host socket.** The user types `hi`. `scripts/chat.ts` writes `{"text":"hi"}\n` over a Unix domain socket at `data/cli.sock` (created `chmod 0600` by `src/channels/cli.ts`'s `setup()` — filesystem permissions are the entire authentication mechanism: "connected to this socket" is defined to mean "is the socket's owner").
*Authority: whoever can open that socket file — i.e., the local user account the host process runs as. No NanoClaw-level check happens here at all; it's delegated entirely to the OS.*

**2. CLI adapter parses the line.** `cli.ts`'s `handleLine()` parses the JSON, sees no `to`/`reply_to` routing override, calls `claimChatSlot()` (evicting any other connected terminal), and calls `config.onInbound('local', null, { id, kind:'chat', timestamp, content:{ text:'hi', sender:'cli', senderId:'cli:local' } })`.
*Authority: the CLI adapter, running inside the host's single Node process — same authority as the host itself, since it's just a module of it.*

**3. Host wraps and routes.** `onInbound` (wired in `src/index.ts`) builds an `InboundEvent{ channelType:'cli', platformId:'local', threadId:null, message }` and calls `routeInbound()` in `src/router.ts`. Inside:
   - No message interceptor claims it (those exist for card-reply capture flows, not plain chat).
   - `getChannelAdapter('cli')` resolves the live adapter to check `supportsThreads` (false for CLI) — thread id stays null.
   - The `messaging_groups` row for `(cli, local, cli)` is looked up (or, on a fresh install, auto-created — `scripts/init-cli-agent.ts` normally pre-creates it, so this is usually a lookup, not a create).
   - **Sender resolution**: the permissions module's `extractAndUpsertUser` (registered as the router's `senderResolver`) parses `senderId:'cli:local'` and upserts a `users` row if new.
   - **Engagement**: CLI's declared defaults (`CLI_DEFAULTS` in `cli.ts`) set `engageMode:'pattern', engagePattern:'.'` for both dm and group — `'.'` always matches, so the wired agent always engages.
   - **Access gate**: CLI's `unknownSenderPolicy` is `'public'` — the permissions module's access gate short-circuits to allowed with no policy check at all (see `permissions/index.ts`'s `setAccessGate`: `if (mg.unknown_sender_policy === 'public') return { allowed: true }`).
   - `deliverToAgent()` runs: `gateCommand('hi', ...)` in `src/command-gate.ts` sees text doesn't start with `/` → `{action:'pass'}` immediately (no DB lookup even attempted for non-slash text).
*Authority: entirely the TypeScript host process. No privileged decision has been made yet — everything so far is ordinary routing logic, none of it guard-gated. This message never touches `guard()` at all, and that turns out to be true for the entire rest of this trace too (see "What this trace confirms" below).*

**4. Session resolved, message queued.** `resolveSession()` finds or creates a `Session` row (session_mode from the wiring — typically `'shared'` for a CLI DM), creating the session folder + preparing its mailbox (`initSessionFolder` → `getAgentMailbox().prepare()`) if new. `writeSessionMessage()` then extracts any attachments (none here) and calls `mailbox.insertMessage(...)` — on the SQLite implementation, this is a direct Node.js write into `data/v2-sessions/<agent_group_id>/<session_id>/inbound.db`'s `messages_in` table: a new row, `status='pending'`, `trigger=1`.
*Authority: the TypeScript host process, via `better-sqlite3` — a plain, synchronous, unauthenticated file write. Nothing between "the router decided to engage" and "the row exists on disk" can be intercepted or vetoed by anything Go-shaped, because nothing Go-shaped exists in this path today.*

**5. Container is woken.** `wakeContainer(session)` (`src/container-runner.ts`) is called. If no container is already running for this session, `spawnContainer()` composes a `SessionSpec` (`composeSessionSpec` — image, mounts classed `group-state`/`install-surface`/`allowlisted-extra`, resource limits, `runAs` uid/gid) and hands it to the selected `SessionDriver`, which (for the Docker driver) shells out to `docker run` directly.
*Authority: **the TypeScript host process, exclusively.** This is the single most consequential authority point in the entire ordinary-chat path, and it is worth stating plainly: today, nothing stands between "the host process decided a container should run" and "a container is actually running" — no guard consult, no second process's approval, no compiled boundary. This is exactly the "session/runtime admission" seam the second-opinion review (recorded in the project doc) flagged as the real first security milestone for a Go kernel. The concern isn't that spawning a container to answer a chat message is unsafe — it isn't; that's the system working as designed. It's that whatever process holds this authority today is the same process that would need to lose it for a Go kernel's enforcement to be structurally exclusive rather than advisory.*

**6. Container reads the queued message.** Inside the already-running (or freshly-spawned) container, `container/agent-runner/src/index.ts`'s `main()` has called `runPollLoop()` (`poll-loop.ts`), a `while (true)` loop polling every ~1s. It calls `getPendingMessages(isFirstPoll)` — the container's own mailbox implementation (Bun's SQLite bindings) reading the *same file* the host just wrote to, filters out `kind:'system'` rows, sees our message has `trigger:1`, and calls `markProcessing([id])` — a status flip written back into `inbound.db` from the container side.
*Authority: the containerized Bun process — sandboxed by whatever Docker actually enforces on the mounts/network/uid composed in step 5 (there is no additional in-process check here; the container trusts the mailbox file's contents completely once it's inside the sandbox Docker set up for it). The coordination between host and container on this one SQLite file is filesystem-level (WAL locking), not IPC — there is no message bus, no socket, no RPC between these two processes; the shared file **is** the entire protocol.*

**7. The agent turn runs.** `poll-loop.ts` formats the pending message(s) into a prompt (`formatMessagesWithCommands`) and calls `config.provider.query({ prompt, continuation, cwd, systemContext })` — the Claude provider (`container/agent-runner/src/providers/claude.ts`, not read in this pass) invoking the Claude Agent SDK, which runs the actual LLM turn and may call MCP tools exposed by the `nanoclaw` MCP server (`mcp-tools/index.ts` → `mcp-tools/core.ts`, e.g. `send_message`).
*Authority: the Claude Agent SDK subprocess, inside the container, inside whatever Docker sandbox and egress-lockdown network (`src/egress-lockdown.ts`, if enabled) the host composed. Any credential the model needs (e.g. the Anthropic API key) is injected by OneCLI at the gateway hop, never handed to this process directly — confirmed in P1-01's read of `src/providers/claude.ts` and `src/config.ts`.*

**8. Reply is written to the outbound mailbox.** Two possible paths, both ending the same way:
   - The model's final text contains a `<message to="cli">...</message>` block — `dispatchResultText` (or, for a streaming-capable provider, `deliverMidTurnBlocks` mid-turn) parses it and calls `sendToDestination`, which calls `writeMessageOut(...)`.
   - The model instead calls the `send_message` MCP tool directly (`mcp-tools/core.ts`) — same terminal call, `writeMessageOut(...)`.
   Either way, `container/agent-runner/src/db/messages-out.ts`'s `writeMessageOut` goes through `getAgentMailbox().operations.writeMessageOut(...)` — a write into `outbound.db`'s `messages_out` table. `markCompleted([id])` then flips the original `messages_in` row to `status='completed'`.
*Authority: the containerized Bun process again — this is the container's own file, and the container is its sole writer for message content (the host only ever reads `outbound.db`, per `delivery.ts`'s own comment: "reads runner-owned outbound state read-only"). This is the mirror image of step 4: there, the host wrote and the container read; here, the container writes and the host reads.*

**9. Host delivery poll picks it up.** `src/delivery.ts`'s `pollActive()` (1s interval, for sessions with a live container) calls `deliverSessionMessages(session)` → `drainSession()`, which reads `getDeliveredIds()` / `getDueMessages()` from the session's mailbox (a read of `outbound.db`), finds our new row, and calls `deliverMessage()`. Since `channelType`/`platformId` are set and this is the session's own origin chat, the permission check (step in `deliverMessage` that would otherwise require an `agent_destinations` row) passes automatically — replying to the chat you were spawned from needs no explicit grant.
*Authority: the TypeScript host process — this is a read of container-owned state, not a privileged act by itself.*

**10. Delivery to the real world.** `deliverMessage()` calls `deliveryAdapter.deliver('cli', 'local', null, 'chat', content, undefined, undefined)` — the delivery bridge built by `createChannelDeliveryAdapter()` in `channel-registry.ts`, which resolves the **exact** live CLI adapter instance and calls its `.deliver()`. `cli.ts`'s `deliver()` extracts the text and, if a terminal is still connected, calls `client.write(JSON.stringify({text})+'\n')` over the same Unix socket from step 1. `markDelivered(msg.id, undefined)` then records the delivery — as a marker written into **`inbound.db`** (the host's own file), not `outbound.db`, which is why the host never needs write access to the container's file at all.
*Authority: the TypeScript host process, exclusively — this is the one step in the entire trace where a real external effect (bytes reaching the user, or for a real platform, an outbound API call to WhatsApp/Telegram/Slack) happens, and it can only happen here. The container never holds channel credentials and never talks to the outside world directly; every outbound effect a user actually sees is mediated by this one host-side call.*

## What this trace confirms

**Zero `guard()` consults happen anywhere in this path.** An ordinary chat message — from arrival to reply — never once reaches `src/guard/guard.ts`. That is exactly consistent with LAW-07 ("Go enforces what must never be bypassed; TypeScript decides most user-facing behaviour") and with P1-01's classification of the router, session manager (routing logic), delivery, and permissions module as KEEP TYPESCRIPT: none of the ten steps above are "privileged actions" in the sense `guard()` exists for (those are things like `create_agent`, `install_packages`, `add_mcp_server`, channel registration, sender approval — a separate, narrower set of code paths this trace deliberately did not need to exercise). This is a genuinely useful, somewhat reassuring finding for the second-opinion review's "exclusive enforcement" question: the ordinary hot path and the guarded-action path are already cleanly separated in the existing codebase. A Go kernel guarding privileged actions would not need to sit in this path at all, and should not — inserting it here would violate LAW-02 (no Go for ordinary customization) for no security benefit, since nothing here is a privileged action.

**Two processes, one shared file each way, no IPC.** The host and container never talk to each other directly — not a socket, not a pipe, not an RPC call. `inbound.db` flows host→container (host writes messages and delivery markers, container writes status transitions); `outbound.db` flows container→host (container writes replies, host only reads). `src/mailbox/model.ts`'s strict record parser is the entire wire contract, enforced independently on each side because the two processes share no runtime module (by design, per that file's own header comment). This is precisely why P1-01 flagged `mailbox/model.ts` as a BOUNDARY component: a future Go host would need a faithful transcription of this exact parser, differentially tested against the TypeScript one, or the two sides of this file-based protocol silently drift.

**Container spawn (step 5) is the one real "who holds authority" finding worth carrying forward.** Every other step in this trace is either read-only, or a write to a file the writer already fully owns (host owns `inbound.db` content + delivery markers; container owns `outbound.db` content). Step 5 is different: it is the one place a single process (the TypeScript host) unilaterally causes a new, real OS-level resource (a Docker container, with its own mounts and network) to come into existence, with no checkpoint of any kind. That is not a bug — nothing about answering a chat message should require approval. But it is the concrete, traced answer to the second-opinion review's question "which process currently possesses the authority to cause the real-world effect": for container creation, today, it is unconditionally the TypeScript host process. `container-runner.ts`'s `composeSessionSpec`/`buildMounts` (already flagged UNDECIDED-leaning-GO-KERNEL in P1-01) is where that authority would have to move for a Go kernel's enforcement of mount/resource invariants to be structural rather than advisory.

## Deliberately out of scope for this pass

- **Privileged/guarded actions** (e.g. `install_packages`, `create_agent`, `add_mcp_server`, channel registration): these follow a different, already well-understood path — `registerDeliveryAction` with a `DeliveryGuardSpec` (`src/delivery-guard.ts`'s `runGuarded`: precheck → `guard()` consult → deny/hold/allow → handler), fully traced during P1-01's read of `guard.ts`. Not re-traced end-to-end here since the ordinary-message trace above is the one that needed proving; P1-03's `grantCoversRequest` audit is the right place to trace a privileged action's approval-to-execution path in the same level of detail.
- **`container/agent-runner/src/providers/claude.ts`** (27.8 KB) — the actual Claude Agent SDK integration inside step 7 — was not read line-by-line. What's documented above (credential injection via OneCLI, no direct key exposure) is carried forward from P1-01's read of the host-side `src/providers/claude.ts`, not independently re-verified on the container side this pass.
- **The concrete Docker driver** (`src/drivers/`, referenced but not opened) — step 5 says "shells out to `docker run`" based on `container-runner.ts`'s own comments and imports, not a direct read of the driver implementation.
- **A non-CLI channel's inbound/outbound adapter code** (e.g. `chat-sdk-bridge.ts`, 46 KB, or `whatsapp.ts`, 46.8 KB) — the CLI adapter was chosen specifically to avoid needing to read either of these large, platform-specific files; the claim that "everything in between is identical" rests on the adapter interface contract (`src/channels/adapter.ts`, fully read in P1-01), not on reading every adapter.
