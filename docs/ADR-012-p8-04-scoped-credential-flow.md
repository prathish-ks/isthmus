# ADR-012: Scoped/Temporary Credential Flow Prototype (P8-04)

Status: accepted, 2026-09-02, as task P8-04. Prerequisite: P5-05 (satisfied). Done when, per the master plan: "Prototype + tests + ADR clearly state improvement/limitations."

## What was built

`internal/credentialbroker` — a `Broker` that issues short-lived, scoped `Token`s and resolves a still-live one back to its underlying secret value. The core property this prototype demonstrates, proven directly by `TestBuildAgentEnv_NeverContainsTheSecretValue`, is that an agent container's env can be built using only a `Token`'s opaque `ID` (a short, non-credential-shaped string, checked against `mount.LooksLikeCredential` as a backstop — the same function `internal/credential`'s own tests already use). The real secret value never leaves the `Broker` except through `Resolve`, which enforces expiry as an actual check (`ErrExpiredToken`), not a documented expectation. `Token` itself has no field capable of holding a secret at all (`TestToken_HasNoSecretField` pins this structurally, the same "no such field exists" discipline `internal/kernel.CapabilityRequestPayload` already applies to its build-context directory).

This is explicitly a second, narrower mechanism alongside `internal/credential` (P5-05), not a replacement for it. `internal/credential` already proves the real, shipped OneCLI flow never puts a value in env (`security.TestInvariant_RealCredentialFlowNeverPutsAValueInEnv`) via a mounted-file reference; this prototype explores a token/broker shape instead, per this task's own instruction to prototype "one temporary/scoped credential flow in isolation."

## Improvement over the baseline this prototypes an alternative to

A long-lived credential handed to a container once, at wake time, is valid for the container's entire lifetime — if the container or the value it holds is ever exfiltrated, the credential remains usable until an operator notices and manually revokes it. This prototype's token has a bounded lifetime by construction (`ExpiresAt` is a required field, not optional — see `docs/capabilities.md`'s misuse-case #1, "a grant that never expires"). `Revoke` demonstrates invalidating one before its natural expiry. Both properties are proven by tests using an injected clock rather than asserted only in prose (`TestResolve_WorksDuringWindowThenFailsAfterExpiry`, `TestRevoke_InvalidatesResolveAndValidateBeforeNaturalExpiry`). The scope check (`Validate`'s `expectedScope` parameter) additionally means a token minted for one purpose (e.g. `chat`) is structurally rejected when presented for another (`admin`) — narrower blast radius than a single credential valid for every operation a provider's API key can perform.

## Limitations, stated plainly rather than glossed over

1. **This is a prototype, explicitly not wired into any live request path.** Nothing in `internal/kernel`, `container-runner.ts`, or the real OneCLI gateway calls `credentialbroker` today. Promoting it to production status would require deciding who calls `Issue` (at `container.wake` time, inside `internal/kernel`?) and who calls `Resolve` (the OneCLI proxy process, which is TypeScript today, not Go) — genuine cross-language wiring work this ADR does not attempt.
2. **In-memory only, single process.** A `Broker` restarted loses every issued token, and there is no mechanism here for a token issued by one process to be resolved by another — a real deployment (host process issuing, gateway/proxy process resolving) would need the broker to be a shared service or a durable store, neither of which exists in this prototype.
3. **No rate limiting or issuance quota.** Nothing in this package stops a caller from calling `Issue` in a tight loop; a real deployment would likely want to bound how many live tokens one session can hold at once, the same way P8-02's read-only filesystem grants might eventually want an equivalent bound. Not implemented here — the task's own scope is "one temporary/scoped credential flow," not a general rate-limiting layer.
4. **`Resolve`'s trust boundary is a comment, not an enforced one.** The package doc says "only a trusted gateway/proxy should call Resolve, never the agent container" — but `Resolve` is an exported method any caller in-process can call. Enforcing that boundary for real would mean putting the agent side and the resolving side in genuinely separate processes (which the real architecture already does — the agent runs in a Docker container, the resolving side would run in the host process). This differs from relying on a Go-level access modifier that can't express "some callers of this package, but not others."
5. **No renewal flow.** A token that's about to expire has no path to "extend this token's life without re-issuing" — the caller re-requests a fresh `Issue`. Whether that's the right UX (vs. a renewal call) is an open design question this prototype doesn't need to answer to prove its core security property.

None of these limitations are security regressions relative to today's real flow (which this prototype doesn't touch). They are gaps between "a prototype that proves a property in isolation" and "a production mechanism," named explicitly so a future phase adopting this shape knows what's still open rather than assuming the prototype is deployment-ready.
