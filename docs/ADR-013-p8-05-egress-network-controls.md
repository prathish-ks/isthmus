# ADR-013: Egress/Network Controls Evaluation (P8-05)

Status: accepted, 2026-09-02, as task P8-05. Prerequisite: P5-06 (satisfied). Done when, per the master plan: "ADR says Implement / Defer / Reject with evidence." Instruction: "Measure whether outbound allowlisting/proxying improves containment without breaking common tools. Prototype only if justified... Do not implement unless security benefit clearly exceeds compatibility/friction cost."

## Why this is three decisions, not one

R-08 in the master plan's own risk register names the exact failure mode a single blanket answer would risk: "Egress restrictions... Common tools silently break... Trigger to stop/redesign: Compatibility loss exceeds security value." `egress-lockdown.ts` has been a named open item since P5-05 (`internal/credential`'s own doc comment: "verify egress-lockdown.ts's network-isolation guarantee... remains an open item from the Opus readiness review, not resolved by this task"). Evaluating it properly means separating what NanoClaw agent containers actually need network access for (arbitrary web search, arbitrary API calls, arbitrary MCP tool servers — LAW-02's "no Go for ordinary customization" applies to network destinations exactly as much as it applies to skills) from the one class of destination no legitimate customization has ever needed to reach.

## Decision 1: general outbound domain allowlisting — **Defer**

**Evidence against implementing now**: NanoClaw's whole value proposition (OBJ-02/OBJ-03, the Preservation Matrix's "AI-native customization"/"MCP/tools ecosystem" rows) depends on an agent being able to install a new skill or wire up a new MCP tool server without asking a human to also edit a network allowlist. A representative sample of what agent containers legitimately reach today — package registries (npm, PyPI, crates.io) for tool installation, arbitrary third-party APIs an MCP tool wraps, the model provider's own API, web-search backends — has no stable, enumerable domain set. An allowlist strict enough to matter would need constant manual updates or would need to default-permit unknown domains (which defeats the point), and R-08's own "common tools silently break" second-order effect is exactly what a strict allowlist produces the first time a user adds a skill that calls a new API.

**What would change this decision**: a concrete, repeated incident report of exfiltration via agent network access, or a NanoClaw upstream feature that already scopes network access per-skill (in which case this project would evaluate reusing that contract per LAW-03, rather than inventing a parallel one) — neither exists today.

## Decision 2: an outbound proxy (all traffic routed through a host-controlled point, logged/inspectable) — **Defer**

**Evidence against implementing now**: this is a heavier version of Decision 1's problem plus a new one — a proxy is a new long-lived component (LAW-05: "every component must justify itself") that would need TLS interception to inspect HTTPS traffic (the overwhelming majority of what any agent tool talks), which means either breaking certificate pinning in tools that use it or accepting a proxy that can only see destination hosts, not content — at which point it provides strictly less information than Decision 3's targeted check below, for strictly more operational complexity (a proxy that must stay up for every container to have network access at all is a new single point of failure this personal-agent host doesn't have today). R-11's "no dashboard/SSO/K8s/HA before beta proof" restraint applies by extension: a traffic-inspecting proxy is exactly the kind of enterprise-shaped feature this project's own risk register warns against building before there's beta evidence it's needed.

## Decision 3: blocking cloud-metadata / link-local destinations — **Implement** (design decided here; code deferred to the exec-argv seam, not written in this pass)

**Evidence for implementing**: this is a structurally different case from Decisions 1-2. The link-local address range (`169.254.0.0/16`, and specifically `169.254.169.254`, the address every major cloud provider — AWS, GCP, Azure — uses for their instance-metadata service) is the single most common real-world container-escape/credential-theft vector in production incident reports industry-wide: a compromised or malicious process inside a container requests `http://169.254.169.254/latest/meta-data/iam/security-credentials/` and receives the *host's own cloud IAM credentials*, with no authentication required by design (that's the whole point of the metadata service — it trusts network topology as its authorization). No legitimate NanoClaw skill, MCP tool, or agent workflow has a reason to reach this address; blocking it has effectively zero compatibility cost, which is exactly what distinguishes it from Decisions 1-2 (R-08's own mitigation list — "scoped exceptions" — describes this shape precisely: a narrow, well-justified exception to "otherwise permit," not a default-deny posture).

**Why this counts as "improves containment without breaking common tools"** (the task's own success criterion): every other destination remains fully reachable — this is not an allowlist, it is a single, well-known denylist entry with a threat model specific enough to name (cloud-metadata credential theft) rather than a general posture that would need re-justifying against every future skill.

**Where this would actually be implemented, not invented here**: `internal/kernel/exec.go`'s `dockerExecutor` already constructs the exact `docker run` argv this project's containers launch with (`containerdefaults.UserArgs`/`ResourceArgs`/`PidsLimitArg` compose into it today). Blocking metadata-service reachability is a Docker-level concern at that same seam — either an `--add-host=169.254.169.254:127.0.0.1`-style override, or (more robustly, since a container can still resolve the literal IP without DNS) a firewall/iptables rule scoped to the container's network namespace at spawn time. Concretely deciding between those two mechanisms, and writing the code, is deferred to whichever task next touches `exec.go`'s argv construction — this ADR's job (per P8-05's own done-when, "ADR says Implement/Defer/Reject with evidence") is recording the decision and its justification, not necessarily shipping the code in the same pass; the master plan's own instruction for this task is "Prototype only if justified," and a one-line argv change is small enough to fold into that future task rather than needing a separate prototype step here.

## Summary

| Control | Decision | Why |
|---|---|---|
| General outbound domain allowlisting | Defer | Breaks arbitrary future skills/MCP tools by design; no stable enumerable domain set exists (LAW-02, R-08) |
| Outbound TLS-inspecting proxy | Defer | New long-lived component with a single-point-of-failure risk and either broken cert pinning or reduced visibility; no beta evidence justifies the complexity (LAW-05, R-11) |
| Block cloud-metadata / link-local addresses | **Implement** (design decided, code deferred to the exec-argv seam) | Near-zero compatibility cost, addresses a well-known, specific, severe threat (host credential theft via SSRF) that has no legitimate use case to preserve |

This resolves the P5-05-era open item on `egress-lockdown.ts` to the extent P8-05 asks: not by porting that file wholesale (nothing in it has decision logic to port — internal/credential's own doc comment already established that), but by evaluating what a Go-kernel-enforced egress control should and shouldn't do, with the one narrow control that clears the bar recorded here for future implementation rather than left as an unexamined open item.
